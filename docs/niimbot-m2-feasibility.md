# NIIMBOT M2 feasibility notes

## Current app state

The production Summary tab already renders 50mm x 30mm browser-print labels with
CSS `@page` sizing. That remains the safest fallback because it uses the OS print
dialog and the vendor desktop driver path if the printer is installed over USB.

This spike adds a Web Bluetooth probe to the Summary tab. It checks whether the
browser can select the M2 and resolve the common NIIMBOT BLE service and write
characteristic. It does not send print commands yet.

## Known M2 details

- Model family: NIIMBOT M2 / M2_H, thermal transfer.
- Tested USB model name: `NIIMBOT M2_H LABEL PRINTER`.
- Tested USB vendor/product: `0x3513 / 0x0002`.
- Tested serial: `M2_H-I409130491`.
- Tested macOS serial device: `/dev/cu.usbmodem1101`.
- Read-only identity query response:
  `#10001:V01.01,M2_H-I409130491,1*7C#`.
- Resolution: 300 DPI.
- Effective printhead: about 48mm, 567px.
- Label widths: 20-50mm.
- Common included label: 50mm x 30mm.
- Connections advertised by NIIMBOT: Bluetooth and Type-C/PC.

## Integration paths

1. Official NIIMBOT SDK
   - Best long-term path if NIIMBOT grants SDK access.
   - Their developer support page says they provide SDKs, APIs, guides, demos,
     and support for Web, C++, C#, Android, iOS, Flutter, uni-app, WeChat, and
     DingTalk mini-programs.
   - Action: submit the developer support request and ask specifically for the
     Web SDK, M2/M2_H support, print-image API, status/error API, and licensing
     terms.

2. Browser print fallback
   - Already implemented.
   - Uses `window.print()` and CSS label sizing.
   - Best short-term path for delivery work because it avoids private protocols.
   - Needs physical calibration for margins, orientation, density, and whether
     the OS driver respects 50mm x 30mm page size.

3. Web Bluetooth direct integration
   - Feasible only in browsers with Web Bluetooth support, mainly Chromium-based
     desktop/Android browsers.
   - iOS Safari is not a viable direct-Bluetooth target.
   - Community protocol docs identify a common BLE service UUID
     `e7810a71-73ae-499d-8c15-faa9aef0c3f2` and characteristic UUID
     `bef8d6c9-9c21-4c9e-b632-bd58c1009f9f`.
   - Next step after device probe: send a harmless status/version command, then
     generate a 300 DPI monochrome raster payload for the current label layout.

4. Local bridge service
   - If browser Bluetooth is too limited, a small local Node/Python/native bridge
     could talk USB/Bluetooth serial and expose `POST /print-labels` to the web
     app.
   - More operational overhead, but usually better than reverse-engineering BLE
     in the browser if this must work reliably on set.
   - Current next step: use `npm run niimbot:probe` to confirm the USB serial
     identity/version query path before sending any print, feed, beep, motor, or
     state-mutating commands.

## Test checklist when the printer arrives

1. Install the NIIMBOT app and print the same 50mm x 30mm label from the vendor
   app to verify ribbon, label roll, alignment, and density.
2. Open this app in Chrome or Edge, go to a production Summary tab, and tap
   `Check M2`.
3. Record whether the device appears, whether the probe finds the characteristic,
   and the exact browser/OS used.
4. Use `Print labels` and calibrate CSS if the label content is shifted, clipped,
   rotated, or scaled.
5. If the BLE probe passes, add a direct-print experiment behind a feature flag.
6. If the BLE probe fails but USB printing works, prioritize the browser-print or
   local-bridge path.

## Open questions for NIIMBOT

- Is the Web SDK publicly usable in a normal browser app, or does it require a
  native helper/driver?
- Does the SDK support M2/M2_H thermal transfer models specifically?
- Can it print arbitrary raster images generated by our app?
- Can it report label size, media/ribbon status, lid-open, low battery, and print
  completion?
- Are there cloud, account, or label-consumable checks that can block offline use?
